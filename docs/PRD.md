# PRD — 가맹점 위험도 조회분석 AI 에이전트

> PG사 컴플라이언스 심사를 위한 내부 도구. Next.js 16 + SQLite + `claude -p` 멀티에이전트 기반.
> 이 문서는 프로젝트 전체를 규정하며, 아래 **Features** 목록의 각 항목은 `docs/specs/<name>.md`로 개별 스펙화된다.

## Problem Statement

PG(결제대행)사는 신규 가맹점을 받을 때마다 그 가맹점이 도박·성인·대부 같은 고위험/금칙 업종은 아닌지, 신원 정보가 진짜인지, 부정 이력은 없는지, 제출한 서류가 입력 정보와 맞는지를 심사해야 한다. 지금은 이 판단이 심사자 개인의 경험과 수작업에 의존하고, "왜 이 결정을 내렸는가"가 일관되게 기록·감사되지 않는다. 심사 기준도 사람마다 다르게 적용되기 쉽다.

## Solution

컴플라이언스 심사자가 **신규 가맹점을 한 건씩 등록하면, AI 에이전트가 4개 관점(신원·업종·평판·서류)에서 동시에 위험도를 분석하고, 정해진 규칙으로 종합 위험등급과 권고(승인/거절/추가정보)를 산출하며, 근거 보고서를 작성**해 주는 내부 웹 도구다.

심사자는 AI의 권고를 참고하되 **최종 결정은 사람이 내리고, 그 결정과 사유가 결정자·시각과 함께 기록**된다. 가맹점별로 분석 이력이 쌓여 과거 판정을 감사할 수 있고, 심사 기준(관점별 지침)은 코드 수정 없이 화면에서 조정할 수 있다. 결과 보고서는 인쇄/PDF로 보관한다.

대상 사용자: PG사 컴플라이언스 심사 담당자(단일 운영자, 로컬 단일 사용자 환경).

## Features

1. **data-foundation** — 전체 시스템의 데이터 토대. 가맹점·분석·가이드라인·설정 테이블 스키마, 공용 타입, 심사자명 설정, 그리고 첫 실행 시 데모 가맹점·완료 분석·기본 가이드라인을 자동으로 채우는 시드. (다른 모든 기능이 이 위에서 동작)
2. **merchant-intake** — 새 분석을 시작하는 입력 흐름. 심사자가 가맹점 정보(상호명·사업자번호·대표자명·업종·주소·제출서류)를 신규 입력하거나 기존 가맹점을 선택해 분석 레코드를 생성한다.
3. **risk-analysis-engine** — 핵심 AI 에이전트. 4개 관점 에이전트를 병렬로 실행하고 관점별 진행/결과를 실시간으로 스트리밍하며, worst-wins 규칙으로 종합 위험등급·권고를 결정적으로 산출하고, 부분 실패는 격리하며 안전강등을 적용하고, 종합 보고서를 생성한다.
4. **analysis-detail-and-decision** — 분석 상세 화면. 관점별 위험도·근거, 종합 등급·권고, 보고서를 보여주고, 심사자가 최종 결정(승인/거절/추가정보)과 메모를 기록하며, 보고서를 인쇄/PDF로 내보낸다. 실패 건 재실행, 완료 건 재심사(새 레코드)도 여기서 한다.
5. **analysis-browsing** — 쌓인 기록을 둘러보는 기능. 전체 분석 목록(위험등급·권고·상태로 정렬/필터)과, 특정 가맹점의 분석 이력을 시간순으로 보는 가맹점 타임라인.
6. **dashboard** — 심사자의 홈 화면. 미결정 대기·고위험/거절권고·기간별 처리량·권고 분포 KPI 카드와 최근 분석 목록으로 "지금 할 일"을 한눈에 보여준다.
7. **guideline-management** — 관점별 심사 기준(분석 지침 프롬프트)을 화면에서 편집하는 기능. 저장하면 다음 분석부터 반영된다.

## Scope & Priorities

**핵심(코어) — 이게 없으면 제품이 아님**
- `data-foundation` → `merchant-intake` → `risk-analysis-engine` → `analysis-detail-and-decision`

이 4개가 "가맹점 입력 → AI 분석 → 사람 결정"이라는 제품의 본질적 흐름을 완성한다. 빌드 순서도 이 순서를 따른다(뒤 기능이 앞 기능의 데이터·실행 결과에 의존).

**보강 — 핵심 흐름을 실용적으로 만듦**
- `guideline-management` (분석 품질을 운영자가 통제) — `risk-analysis-engine` 직후가 자연스러움
- `analysis-browsing` (이력·감사) — 상세/결정 이후
- `dashboard` (진입점·요약) — 데이터가 쌓인 뒤 마지막에 붙이는 게 자연스러움

권장 빌드 순서: data-foundation → merchant-intake → risk-analysis-engine → analysis-detail-and-decision → guideline-management → analysis-browsing → dashboard

## Out of Scope

실현 가능성 점검에서 명시적으로 제외한 것들:

- **실시간 외부 조회/연동** — 사업자등록 상태 조회 API, 제재·AML 리스트, 실제 웹 평판/뉴스 검색. "평판" 관점은 모델의 학습지식 기반 추정이며 실시간 인터넷 조회가 아니다. (도구 사용 에이전트는 신뢰성·권한 문제로 v1 제외)
- **멀티 사용자 인증/계정** — 로컬 단일 운영자 전제. 결정자는 설정의 심사자명으로만 기록(로그인·세션 없음).
- **파일 업로드 파싱** — 사업자등록증/신청서 파일 자동 추출은 제외, 입력은 수동 폼.
- **정식 PDF 생성 엔진** — 별도 PDF 라이브러리 없이 브라우저 인쇄(print CSS)로 대체.
- **일괄 등록/상시 모니터링** — 온보딩 1건 심사 흐름에 집중. 대량 CSV 등록·주기적 재평가는 제외.
- **자동 승인/거절 집행** — 시스템은 권고만 산출하는 보조 도구이며, 최종 책임은 사람 심사자에게 있다.

## Further Notes

**아키텍처 제약 (CLAUDE.md 준수)**
- 3-tier: Presentation(`app/[page]/page.tsx`) / Application(`app/api/*/route.ts`) / Infrastructure(`lib/db.ts` + `schema.sql`).
- `getDB()`는 `'use client'` 컴포넌트에서 호출 금지. 모든 타입은 `types/index.ts` 단일 관리.
- AI 호출은 `claude -p` 서브프로세스 + SSE 스트리밍 패턴.
- UI는 기존 `components/ui`(Badge/Button/Card/NavLink) 재사용. 응답·문서·UI 카피는 한국어.

**성능·비용 (사용자 합의됨)**
- 분석 1건 = `claude -p` 5회 호출(관점 4 병렬 + 종합 1). 한 건당 수십 초~1분, 자원/비용은 단일 호출의 약 5배. 로컬 단일 사용자 전제이므로 동시 5개 프로세스는 허용.

**판정 규칙 (전역 공통)**
- worst-wins: 최고 관점 위험도가 종합등급 결정 — high→고위험/거절, medium→중위험/추가정보, all low→저위험/승인.
- 안전강등: 실패·누락 관점이 하나라도 있으면 절대 '승인'으로 가지 않고 최소 '추가정보필요'.
- 등급·권고는 규칙으로 결정적 산출, 종합 보고서 서술만 LLM(종합판정 에이전트)이 담당.

**데이터 모델 (전역 공통)**
- `merchants`(영속, 1:N 분석) / `analyses`(상태·관점 JSON·종합등급·권고·사람 최종결정 필드) / `guidelines`(4관점+종합 지침) / `settings`(심사자명 등).
